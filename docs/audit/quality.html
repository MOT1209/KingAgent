ثلاث حالات «الكود يقول غير ما يقوله التعليق»

هذه الأخطر: تعليقات تصف حالة غير موجودة تجعل القارئ يتوقف عن الفحص.

«نموذج تجريبي فقط»

acp-live.js:1 ترويسة الملف: “PROTOTYPE (demo mode only)”. لا شيء في الكود يفحص وضع العرض التجريبي، والمعالج موصول دائمًا في main.js:627. القارئ المتعجّل يقفل الملف على أنه معطَّل. (S1)

«لا تحذف مجلدًا يحمل عمل المستخدم»

agent-remove.js ترويسة سطر ٢ القاعدة صراحةً. الدالة بعدها بثلاثين سطرًا تنفّذ rm -rf على أي مسار تحت $HOME يمرّ فحص «مطلق وتحت المنزل». القاعدة مكتوبة ولم تُنفَّذ. (S3)

«وحدة ميتة» بنية كود حيّة

panel-lifecycle.mjs:280: && !p.dirty && false. الشرط دائمًا خطأ، لكنه يقرأ كنيّة غير مكتملة. المصلح القادم سيصلحه فيغيّر سلوكًا لم يطلبه أحد. (U21)

القاعدة المقترحة: أي تعليق يصف حالة تخطيطية أو نية غير منفَّذة يحتاج علامة TODO صريحة أو يحذف. البحث في src/main/ أعطى صفر TODO/FIXME/HACK — أي أن «غير المكتمل» في هذا المشروع يُقال في صوت واثق لا في علامة تحذير. هذا ما يجعل الحالات الثلاث أعلاهخطرة.

ما يقيسه c8 وما لا يقيسه

package.json يشرح النطاقين في تعليق، والفصل قرار سليم: test:coverage بوابة على src/main و src/core لأنهما يعملان تحت node؛ و test:coverage:renderer تقرير فقط لأن معظم الـ renderer يحتاج DOM.

لكن النتيجة العملية أن الـ renderer — ١٩٬٣٨٥ سطرًا، أكبر من أي طبقة أخرى، و٢٦ من أصل الـ ٩٠ نتيجة — غير مقيس كميّة إطلاقًا. ملاحظة c8 نفسها ذكية: «app.js يحتاج نافذة Electron». هذا صحيح، وهو أيضًا السبب الذي يجعل خللًا في الـ renderer يمرّ إلى الإنتاج. 

npm test              # 2216 اختبارًا
npm run lint          # نظيف
npm run test:coverage # البوابة: main + core
npm run test:coverage:renderer   # تقرير فقط — بلا بوابة
