الأداء: أربعة مسارات تحرق الإطار

المشروع يعرف نمط التجميع بـ requestAnimationFrame ويطبّقه في مواضع صحيحة (markFit/drainFits، وbrowser-pane.schedule). المشكلة أن أربعة مواضع أخرى تكسر نفس القاعدة على مسارات التفاعل اليومية: الكتابة، السحب، التصفية، والتحريك. اثنان منها إصلاحهما كلمة واحدة.

المسارات الأربعة، مرتّبة حسب الكلفة

U5 حاشية المحرر — ٢٠٠٠ تخطيط لكل ضغطة مفتاح

tile-content.mjs:352: gutter.innerHTML = Array.from(rows, (r,i) => \`<div style="height:${r.getBoundingClientRect().height}px">\`)

getBoundingClientRect() داخل دالة Mapper — كل نداء يُفرغ التخطيط المعلّق. وsync() تُستدعى من input (كل ضغطة مفتاح), ومن ResizeObserver، ومن applyMode().

لا تقس الصفوف إطلاقًا. ضع عدّاد CSS على مرآة لعدد الأسطر — لا تحتاج قياسًا البة. إن أصررت على القياس: اقرأ offsetHeight بعد void container.offsetHeight واحدة داخل rAF واحد، ثم خفّف sync() خلف rAF الموجود أصلًا.

U6 حلقة المراقب مع ميل الزجاج

browser-pane.mjs:37 — MutationObserver على document.documentElement يراقب style. وapp.js:1181-1198 initGlassTilt يكتب --rx على .nav-card عند كل rAF أثناء حركة المؤشر.

المسار: حركة مؤشر ← كتابة style ← المراقب يصمد ← schedule() ← layout() يقرأ getClientRects() و getBoundingClientRect() لكل إطار متصفح ثم JSON.stringify للنتيجة كلها. وlayout() يكتب أصنافًا أيضًا في السطر 17، فيطلق Observer ثانية.

إصلاح من كلمة واحدة: احذف 'style' و 'hidden' من attributeFilter. المراقب موجود لالتقاط تغييرات class التي تحرّك الهندسة — لا لالتقاط كل تغيير نمط في المستند. ثم ضيّق النطاق بدل documentElement.
